# WeebX security policy

## Supported version

Security fixes are applied to the latest published WeebX release. Keep WeebX, Windows, Apache, PHP, MariaDB, phpMyAdmin, and every hosted application current.

## Reporting a vulnerability

Do not publish exploit details in a public issue. Use GitHub private vulnerability reporting or a private draft security advisory for `JadaDev/WeebX`. Include the affected version, reproduction steps, impact, attack preconditions, and sanitized supporting logs.

Never attach credentials, database contents, private keys, personal data, or private project files.

## Security model

WeebX provides secure platform defaults for a Windows web-hosting stack:

- Development PHP configuration by default, with an explicit hardened Live / Production profile;
- clear empty/weak/strong MariaDB password status, persistent warnings for weak choices, and Windows encryption for non-empty stored credentials;
- loopback-only MariaDB networking;
- local-only phpMyAdmin and development diagnostics;
- restricted filesystem access, directory listings, dotfiles, and common secret files;
- checksum-verified component downloads, official PHP release discovery, and validated manual PHP imports;
- rejection of unsafe ZIP paths and oversized expanded archives, with an explicit warning that manual PHP validation executes the selected binary;
- disabled PHP session upload progress in both profiles as recommended by PHP's October 23, 2026 advisory;
- guided NTFS permission presets for websites, database data, and runtime files; and
- isolated site profiles with separately generated PHP configuration, session/temp/upload storage, logs, limits, extension sets, path restrictions, NTFS policies, and database identities;
- site database users limited to one database, collision checks that protect unrelated existing accounts, and Windows-encrypted credentials that are omitted from Portal exports;
- validation that managed site names, hostnames, identifiers, and document roots cannot inject configuration or escape the configured `htdocs` boundary; and
- an isolated, sandboxed Electron renderer with a narrow IPC bridge;
- renderer crash recovery that preserves Chromium sandboxing; and
- mandatory Authenticode validation for the default production release command, covering WeebX.exe and the MSI with one trusted signer.

Empty or weak passwords are supported for local development only and are never considered live-ready. Site profiles are defense in depth, not a hostile multi-tenant sandbox: Apache and PHP still run under the same Windows account. Untrusted customers or mutually hostile applications require separate operating-system accounts, containers, virtual machines, or separate hosts. WeebX does not make arbitrary website code safe and cannot configure every surrounding control. Public operators must provide trusted TLS, firewall policy, OS and application patching, backups, monitoring, abuse controls, and incident response. Self-signed certificates generated by WeebX are for local testing, not public production traffic.

Unsigned local builds are development artifacts. Antivirus reputation and native startup trust cannot be guaranteed by application code, so `npm run dist` refuses to create a production release without a trusted Windows code-signing certificate and valid final signatures. Do not publish output from `npm run dist:unsigned`.

See the README's **Before hosting a public website** section before exposing a host.
